= Batch Errors
ifndef::env-site,env-github[]
include::_attributes.adoc[]
endif::[]

Batch processing failures at the record level result in a *Batch Error*. When a Mule app processes records through batch steps, any failure during record processing is captured as a `BatchError` object associated with that specific record.

Batch errors are introduced in *Mule 4.11* and replace the previous exception-based error tracking mechanism. They are basically a wrapper around the xref:mule-error-concept.adoc[] objects generated during record processing, providing additional information about the error and removing the reference to the exception causing the failure.

[[accessing_errors]]
== Accessing Batch Errors

Within a batch step, you can access record errors using these DataWeave functions:

[cols="9a,10a",options="header"]
|===
| DataWeave Function | Description
| `#[Batch::failureErrorForStep(String)]` | Receives the name of a step as a String argument. If the current record presented an error on that step, then it returns the actual `BatchError` object. Otherwise it returns null.
| `#[Batch::getStepErrors()]` | Returns a `Map<String, BatchError>` in which the keys are the name of a batch step in which the current record has failed, and the value is the error itself. +
If the record hasn’t failed in any step, this Map will be empty but will never be null. Also, the Map contains no entries for steps in which the record hasn’t failed.
| `#[Batch::getFirstError()]` | Returns the `BatchError` for the very first step in which the current record has failed. If the record hasn’t failed in any step, then it returns null.
| `#[Batch::getLastError()]` | Returns the `BatchError` for the last step in which the current record has failed. If the record hasn’t failed in any step, then it returns null.
|===

[[selector_expressions]]
== Selector Expressions for Batch Errors

Batch errors are complex data types with several fields, such as a description
and type. When logging and handling Batch errors, can select the values from any
number of the error fields. Taking as an example the error for the first step in which the current record has failed, the following selector expressions are available:

[%header,cols="1,4,3"]
|===
| Field | Description | Selector Expression

|Description
|A description of the problem.
|`#[Batch::getFirstError().description]`

|Detailed Description
|A description of the problem, which can be the same or more extensive than the description.
|`#[Batch::getFirstError().detailedDescription]`

|Type
|A type, used to characterize the problem and allow for routing within an error handler.
|`#[Batch::getFirstError().errorType]`

|Failing Component
|The component where the error was generated.
|`#[Batch::getFirstError().failingComponent]`

|DSL Source
|The DSL source of the failing component.
|`#[Batch::getFirstError().dslSource]`

|Error Message
|An optional Mule message with error data (e.g., HTTP response content for invalid status codes).
|`#[Batch::getFirstError().errorMessage]`

|Child Errors
|An optional collection of inner errors, used by elements like Scatter-Gather to provide aggregated route errors.
|`#[Batch::getFirstError().childErrors]`

|Failure During Handling
|Any error that occurred while handling this error.
|`#[Batch::getFirstError().failureDuringHandling]`

|Stack Trace
|The Java stack trace of the exception.
|`#[Batch::getFirstError().stackTrace]`
|===

[[error_types]]
== Batch Error Types

Batch errors follow the same error type hierarchy as standard Mule errors. A special `MULE:BATCH` error type exists for errors that arise during internal batch processing (rather than chain execution) and don't belong to any specific type.
