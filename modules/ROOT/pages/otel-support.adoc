= OpenTelemetry support in Mule runtime

include::_attributes.adoc[]

:page-aliases: otel, otel support, OpenTelemetry

OpenTelemetry is an observability standard consisting of specifications, APIs, and SDKs. It helps you instrument, generate, collect, and export telemetry data, such as metrics, logs, and traces, to analyze software behavior.

OpenTelemetry enables Mule runtime engine to provide observability into the behavior of Mule apps. With distributed tracing, Mule also brings observability to interactions between Mule apps and non-Mule components that leverage this standard.

Mule supports generating and exporting OpenTelemetry distributed traces and logs. Metrics aren't yet supported through OpenTelemetry.

== Before You Begin

To use the OpenTelemetry Mule features, you must be familiar with:

* Distributed tracing concepts, including traces and spans. 
+
If you're new to distributed tracing and OpenTelemetry, we recommend starting with https://opentelemetry.io/docs/concepts/what-is-opentelemetry/[What is OpenTelemetry] and https://opentelemetry.io/docs/concepts/observability-primer/#understanding-distributed-tracing[Understanding distributed tracing].
* xref:monitoring::telemetry-exporter.adoc[How to export telemetry data to third-party monitoring systems].

Before starting with the observability standard, you must have:

* For OpenTelemetry application tracing, Mule runtime 4.6.0 or later.
* For distributed tracing, Anypoint Connector for HTTP (HTTP Connector) 1.8 or later.
* For OpenTelemetry logs and OpenTelemetry direct export, Mule runtime 4.10.0 version or later.
* Telemetry exporter or Mule runtime direct export configured.

== Tracing a Mule App

Mule leverages OpenTelemetry to provide:

* Application execution observability
+
Tracing a Mule runtime application allow peeking inside its execution while conserving the mental model of a Mule engineer. Their main objective is to intuitively “explain” how the messages are being processed by the Mule application, helping Mule engineers to develop, monitor and troubleshoot.
* Distributed tracing
+
Tracing also enables you to track Mule application interactions. When multiple systems and services are involved, distributed tracing tracks application requests as they flow through distributed environments, providing a comprehensive view of the overall execution.

For example, if an HTTP Listener receives https://www.w3.org/TR/trace-context/[W3C Trace Context] headers, the flow span in Mule acquires the client's remote parent span, the span where the HTTP call originated. Mule automatically propagates the current span to the server endpoints when using the HTTP Requester component. 

The span context format supported for receiving and propagating the context is the https://www.w3.org/TR/trace-context/[W3C Trace Context] format.

=== Mule Span Data

A trace is a sequence of spans representing a complete operation in a distributed system. Spans can be nested and represent a unit of work or operation. Each span includes: 

[%header%autowidth.spread,cols="a,a,a"]
|===
| Categories | Description | Example Values
| Name | Name of the span | `mule:set-variable`
| Parent Span ID | Span ID of current span's parent | `86838830d494d679`
| Start and End Timestamps | Earliest and latest timestamp for a span | `2021-10-22 16:04:01.209458162 +0000 UTC`
| Span Context | Data that uniquely identifies the span: trace ID, span ID, trace flags, and trace state | 
| Attributes | Key-value pairs containing metadata used to annotate a span to carry information about the operation it's tracking. | {
“location”: “flow/processors/2”,
“correlation.id”:  “1234abcd”
}
| Span Events | A structured log message or annotation on a span, used to denote a meaningful, unique point in time during the span's duration. | {
      "name": "",
      "message": "OK",
      "timestamp": "2021-10-22 16:04:01.209512872 +0000 UTC"
    }
| Span Links | Links that associate one span with one or more spans, indicating a causal relationship. | 
| Span Status | Status attached to a span. You can set a span status when a known error, such as an exception, occurs in the app code. | `ERROR`, `OK`, `UNSET`
| Span Kind | Information about how the trace is assembled. | `CLIENT`, `INTERNAL`, `PRODUCER`
|===

=== Example of Flow Tracing Feature

When tracing a flow execution, each Mule component execution involved in processing the message is represented as a span. The component spans describe the relevant aspects of the execution. They can range from a single span for a simple component, such as the Set Payload, to more complex structures, such as a Batch Job.

The Mule runtime traces complex components, such as Batch Jobs.

Next, it displays the Batch Aggregator span, along with the For Each component and the processors within it, such as Transform Message and Logger. 
Then, the trace displays the other two batch steps and their respective components.

=== Errors in Tracing

If the execution of the unit of work represented by a span produces an error, the span's status is set to `Error`. MuleSoft follows the semantic convention defined by OpenTelemetry that adds one or more `exception` events to the span:

* `exception.type`: Mule error type
* `exception.message`: Mule error message
* `exception.stacktrace`: Mule flow stack string representation

In this example, when an error is produced, the span corresponding to the Raise Error component shows an error status in the Lightstep platform: 

image::otel-errors-in-tracing.png["A flow of a telemetry flow with error handling"]

This status propagates to the parent span, for example, the flow span. A detailed view of the span shows the error status and the exception events.

=== HTTP Conventions

The HTTP Listener and HTTP Request operations contribute additional attributes to the spans, providing more context for tracing the HTTP interactions.

For flows with an HTTP Listener:

* Span name: Combination of HTTP Method and path. For example, `POST /api`.
* Span kind: `SERVER`.

Additional attributes for an HTTP Listener associated flow span:

[%header%autowidth.spread]
|===
| Attribute | Description 
| `net.host.name` | Host address of the HTTP Listener
| `net.host.port` | Port of the HTTP Listener
| `http.user_agent` | User agent of the received request
| `http.route` | Path of the HTTP Listener
| `http.method` | HTTP method
| `http.flavor` | HTTP version
|===

For flows with an HTTP Request: 

* Span name: HTTP Method. For example, `GET`.
* Span kind: `CLIENT`.

Additional attributes for an HTTP Request associated flow span:

[%header%autowidth.spread]
|===
| Attribute | Description 
| `http.url` | Target URL
| `net.host.port` | Port of the HTTP Request
| `net.peer.name` | Target IP address
| `http.route` | Path of the HTTP Request
| `http.flavor` | HTTP version
|===

== OpenTelemetry Logs

The Mule runtime implements its logging by leveraging Log4j, where appenders can be configured in order to send logging to different locations: a file, a remote server, etc. Logging levels can also be configured, impacting which log entries will actually be sent.

The OpenTelemetry logging export is implemented along with Log4j logging. This means that users can configure the OpenTelemetry logs export and Log4j appenders at the same time.
Additionally, logging levels must still be configured as part of the Log4j logging configuration and will also apply to the OpenTelemetry logging exporter.

Exported logs will include application, domain and Mule runtime server logs.

=== Mule Log Record Data

OpenTelemetry logging is a sequence of log records with a unified data model, each record corresponding to a Java log call.
Each log record will contain:

[%header%autowidth.spread,cols="a,a,a"]
|===
| Categories | Description | Example Values
| Timestamp | Taken at the moment of the Java log call | `2021-10-22 16:04:01.209458162 +0000 UTC`
| Observed Timestamp | Taken at the moment of the OpenTelemetry log event registration | `2021-10-22 16:04:01.209458162 +0000 UTC`
| Trace ID | The trace where the log event originated. Might not be present if the log occurred outside an application trace. | 4a7b9e1d5c3f8a0e2b6d1f7c8a9e0d2c
| Span ID | The span where the log event originated. Might not be present if the log occurred outside an application trace. | 4b7f3c798460
| Trace Flags | W3C trace flags corresponding to the trace where the log event originated. Might not be present if the log occurred outside an application trace. | 01x
| Severity Text | The severity of the log event. Also known as log level. | INFO
| Body | The body of the log record. Also known as log message. | "Stopping flow: test-flow"
| Instrumentation Scope | Fully qualified name of the Java class where the Java log call originated | "org.mule.runtime.core.internal.lifecycle.AbstractLifecycleManager"
| Attributes | Key-value pairs containing metadata used to annotate a log record to carry information about its context. Will include Log4j MDC entries. | {
“location”: “flow/processors/2”,
“correlation.id”:  “1234abcd”
}
|===

=== Correlation with Traces

OpenTelemetry Log Records define fields for the Trace ID and the Span ID. When tracing is enabled, the Mule runtime will export OpenTelemetry logs that include such values, allowing Application Traces / Application Logs correlation.

If you are not exporting OpenTelemetry logs, you can still correlate the Log4j logs by configuring the MDC logging.
Additionally, any entry added to the Log4j MDC will be added to the OpenTelemetry logs as Log Record attributes, meaning that all the MDC data is exported as part of OpenTelemetry logs.

== Direct export from Mule runtime

Starting with Mule runtime version 4.10.0, OpenTelemetry traces and logs can be configured outside Anypoint Monitoring.
This means that the Mule runtime supports exporting its OpenTelemetry data to a customer managed OpenTelemetry collector instead of the Anypoint Monitoring OpenTelemetry ingestion pipeline.

When using this direct export feature, Anypoint Monitoring OpenTelemetry features will not be available.

=== Recommended architecture for direct export

The Mule runtime supports exporting all its telemetry data using the OpenTelemetry (OTLP) protocol and binary/protobuf format. This means you can configure an endpoint for each signal type (traces and logs) and the data will be sent there.
However, we strongly recommend sending the data to a collector based on the fact that OpenTelemetry collectors enable the most flexible and feature-rich architecture, especially when considering a wide range of use cases and deployment scenarios.

https://opentelemetry.io/docs/collector/

We can highlight these reasons (prioritized):

* Compatibility :

The Mule Runtime must send telemetry signals to one endpoint (the collector) in one (OTEL binary/protobuf) format, achieving vendor neutrality. The collector then is in charge of managing the export of those signals to the selected backends.
Examples where this becomes specially relevant can be the Azure monitoring solutions, which cannot ingest OTEL signals directly and require a specific exporter and the Grafana monitoring solution that implements authentication and additional metrics via collector components.

Exporting the same signal to multiple 3rd party solutions can only be achieved by using a collector. The Mule Runtime configuration only allows one endpoint per signal.

In general, all the 3rd party monitoring solutions are aware of the importance of the collector, with many of them providing their own, supported implementations and assisting in the configuration.

* Security

Applications do not necessarily need external Internet access to reach the external 3rd party monitoring solution.

The collector handles authentication/authorization against the external 3rd party monitoring solution.

The collector can be a single point for dedicated network policies.

* Performance

The collector can be tweaked to achieve its specific goals that differ from the Mule Runtime goals. It can also be configured to scale and to distribute the load independently.

Configuration changes do not affect the Mule runtime instances.

* Observability

Collectors include multiple built in metrics and health checks.

* Centralize data processing

A collector can centralize data enrichment/transformation that is not only meant to be done for the Mule runtime telemetry but also for additional non-Mule service.

=== Direct export configuration

The Mule runtime ships pre-defined configuration templates that allow configuration for both Traces and Logs.

Standalone and Hybrid Standalone:

Users can access and modify the configuration templates as needed. Provided configuration templates include Java system properties placeholders that can be modified or replaced by fixed values if necessary.
Providing all the configuration values when using Java System properties placeholders is not necessary. If a system property is not defined, the default value of the corresponding configuration entry will be used instead.
Tracing and logs export configurations will apply to all the corresponding Mule runtime deployed applications, with no support for individual application configuration.

RTF, CloudHub / CloudHub 2.0:

The Mule runtime configuration templates are internally managed and cannot be accessed or modified. Users must configure the export by setting [secure properties ](https://docs.mulesoft.com/cloudhub/secure-application-properties).

== Advanced features

=== Custom service name and namespace

Service attributes identify the source of the telemetry data. The Mule runtime supports setting the service.name and service.namespace to custom values:

|===
| mule.openTelemetry.tracer.exporter.resource.service.name | Artifact ID | Service name used by the exporter for traces.
| mule.openTelemetry.tracer.exporter.resource.service.namespace | mule | Service namespace used by the exporter for traces.
| mule.openTelemetry.logging.exporter.resource.service.name | Artifact ID | Service name used by the exporter for logs.
| mule.openTelemetry.logging.exporter.resource.service.namespace | mule | Service namespace used by the exporter for logs.
|===

Notes:

* The configured service namespace will apply to both traces and logs.
* For Standalone and Hybrid Standalone, setting a custom service namespace will apply to all the applications deployed and setting service.name is not supported.

=== Custom attributes

Adding custom data to the generated spans and log records can serve multiple purposes. Here are the main ones:

* Adding business context, such as an order id.
* Adding user context, such as a user id.
* Enable filtering and search.
* Improve troubleshooting by adding debug/troubleshoot data.

The Mule Runtime supports adding custom attributes to the spans and log records via the Tracing module: https://docs.mulesoft.com/tracing-module/latest/tracing-module-reference.
Any logging variable set by the module is also added as an attribute of the span that represents the set-logging-variable operation and the spans and log records that are generated for the rest of the flow’s execution, including subflows, flow references and error handlers.

While useful, custom attributes must be handled with care. Relevant information must be included, but an excessive amount of attributes can considerably affect performance and reach the feature limits. Current limits are:

* Maximum of 128 attributes per span (additional attributes will be dropped).
* Maximum length of 16384 bytes per attribute (exceeding bytes will be truncated).

=== Backpressure strategy

Backpressure is manifested for both traces and logs at their export queues, which can get full. Backpressure strategies define how to deal with that event:

* Traces backpressure: Spans that cannot enter the queue when it’s full are dropped.
* Logs backpressure: Default strategy is to block until space is generated for the log records that cannot enter the export queue. This matches the behavior of the Log4j logging. Additionally,  drop strategy can also be configured.

In the event of spans or log records drop, a WARNING log is generated. Internal statistics are tracked about the total drops, so the log messages will show the totals.

Example of drop warning:

"Export queue overflow: 1 spans have been dropped. Total spans dropped since the export started: 2"

=== Tracing levels

The Mule Runtime tracing is structured in a way that offers a base tracing level that can be OVERVIEW, MONITORING or DEBUG.
Every generated span has a corresponding tracing level, so flow spans are of level OVERVIEW, flow component spans are of level MONITORING, and flow component internal execution spans (parameter resolution, connection obtention, etc.) are of level DEBUG.

Under normal circumstances, the default tracing level is the best choice. However, troubleshooting might require a tracing level of DEBUG.

=== Tracing sampling

Sampling is an effective way to reduce the costs of observability.
The Mule Runtime supports what is called HEAD sampling, meaning that the sampling decision is made as early as possible. In the case of a Mule application, that moment is when a message source is about to trigger a message processing (for example, an HTTP listener has received a request).

The HEAD sampling feature is a good fit for:

* Support use cases with limited budgets for observability.
* Accommodate use cases when there might not be a collector involved (consider early development stages) where observability could also be useful.

Regarding decision algorithms, the Mule Runtime currently support the following standardized OpenTelemetry algorithms:

AlwaysOn, AlwaysOff, ParentBasedAlwaysOn, ParentBasedAlwaysOff, TraceIdRatio and ParentBasedTraceIdRatio.

While Head sampling presents simplicity and performance as their best qualities, it has some drawbacks regarding visibility. Examples are:

* Always sampling traces that contain an error.
* Sampling traces based on overall latency.
* Sampling traces based on the presence or value of specific attributes on one or more spans in a trace; for example, sampling more traces originating from a newly deployed service.
* Applying different sampling rates to traces based on certain criteria, such as when traces only come from low-volume services versus traces with high-volume services.

There is another sampling technique that is meant for this complex use cases, called TAIL sampling. Unfortunately, tail sampling is costly and in many cases can compromise the Mule Runtime efficiency. This is the main reason for the Mule Runtime to only support HEAD sampling.
TAIL sampling, when needed, must be implemented at the OpenTelemetry collector.

=== Retry logic

In the case of errors during the export requests, a mechanism of exponential back-off with jitter will try to avoid overwhelming the destination until recovery.
Only errors marked as retriable as per OpenTelemetry standards will be taken into account for the retry logic:

* https://opentelemetry.io/docs/specs/otlp/#failures HTTP transport protocol reference.
* https://opentelemetry.io/docs/specs/otlp/#retryable-response-codes gRPC transport protocol reference.
